## Why

A pair runs on one pod today (L4b) but nothing on the host can launch, watch, collect or resume one: the launch refuses a pair and carries no sealed ceiling, the collection reads one result per request, the resume builder reads flat `run/` only, the wave monitor binds one run per request, and the completion snapshot re-uploads every checkpoint as a second single PUT (measured on quote v4, pod qkfduyfla3b6rt, 2026-10-28: three copies of 1,149,203,227 bytes, one `ReadTimeoutError` that three retries did not recover, a complete 1000-step workload ended `execution_defect` at `final_snapshot`, and the failure snapshot re-published 62 files for 1,382.7 s on a billing pod). At the pilot (steps/250 checkpoints x 4 cells x 8 blocks) the duplicate bytes multiply. L5's block driver (W3) consumes exactly this slice.

## Design (brief-ready)

1. **Launch v5 (D7), `h-probe-launch-v5`.** Generic over stage and class; carries the authority digest (as v4), the GPU class, the sealed hourly price ceiling and the hours cap (both copied from the authority at construction and re-verified against it), and the pair flag plus both cell identities for a pair request. `require_hourly_rate_within_cap` becomes a derivation: `h_probe_command` reads the ceiling from the launch and refuses a `--max-hourly-rate` flag that disagrees with it by name (the flag stays accepted for a smoke launch, which keeps v3 semantics); the controller's `cost_per_hour` check (`h_probe_controller.py:481-482`) reads the sealed value. Pod name stays `<stage>-<class>-<digest prefix>` (v5 digests move, so pod names move; v3 and v4 read-back keep their names). Template environment: the eight-key scientific template of LAUNCH SCHEMA v4 unchanged. v2 read retired (C-L4c-1).
2. **Capture by reference.** The completion and failure snapshots publish a capture copy of an object the pod already published under `run/<cell>/` as a REFERENCE record (same path under `capture/<cell>/`, same `sha256` and `size_bytes`, plus `reference: run/<cell>/<file>`), never a second body; the host collection resolves a reference by reading the referenced object once and verifying its digest. Objects above a declared threshold go multipart with per-part sha256 verification in `d1_trainer_s3_object_adapter` (a non-member); the threshold's home is a gate corner (recommendation: an adapter constant sized from the measured dev-width checkpoint, 182 MB on 2026-10-27, and NOT a new `TransferLimits` field, which would move the v3 canonical form). The capture manifest keeps its name if the gate reads a reference entry as additive; otherwise it is the slice's second schema bump, named in the read-old table.
3. **Host pair collection.** `collect_probe_terminal` (`h_probe_collection.py:50`) gains the pair shape: `h-probe-terminal-collection-v2` with one entry per cell (receipt, result entry, capture root, verification root), the pair verdict and the terminal it was collected under (`complete`, `paused`, `stopped`, `excluded`, `failure`); v1 stays for single-profile requests byte for byte; a pair collection presented as v1 is refused by name with the minimum version. The reader reads result v2 under a failure terminal (DH-47) and keys on the verdict. A pair whose pod died before its first cell began (no MLflow run, no observability directory, no `worker.end`, because `worker_command._PairCellSinks.begin` is the only sink build) collects as a typed `pair_not_started` failure, never as a missing pod.
4. **Per-cell resume (C-L4c-2) and the three death cases.** `build_resume_request` (`h_probe_resume.py:61`) reads `run/<cell>/` (today flat `run/*` only, `:48-57`, status `paused` at `:104`): donor death during warm-up resumes the donor from its last receipt; death after donor training re-materializes the recipient from inputs under `run/donor/` (R3, no hand-off receipt); recipient death resumes the recipient per cell with the donor's root as an input. `h_resumed_run` admits a recipient lineage starting at `warmup_steps + 1` with zero warm-up rows only with hand-off evidence (R2); a lineage without it that starts past step 1 stays refused.
5. **Wave monitor.** `h_wave_monitor._arms` (`composition/entrypoints/h_wave_monitor.py:334-359`) lists one arm per (request, cell): cell runs are named `h-worker-<cell profile identity>` (`run_name_for`, `:150`) with tags `block, pair, cell, run_authority` and the shared `request_sha256` filter (`:224-228`), so the arm filter adds `tags.cell`; a single-profile launch keeps one arm. `tests/test_h_wave_monitor.py` is this slice's.
6. **Stop verb.** `request_stop` admits a pair when `--at-cell` names a cell and publishes the v2 marker `{phase, step, cell}`; a pair without `--at-cell` and a cell on a single-profile request stay refused by name.
7. **Host CUDA pair verifier.** A CPU-mapped verifier over collected bytes, equal to `admit_codec_pair` on L4a's pair fixture (same `VerifiedHandoff` fields); teeth from L4a's `ADMIT_HAZARDS` table.
8. **K-suite.** `scripts/h0_final_probe_checks.py` refuses a pair by name (`:79`, typecheck-forced in L4b, untested); the K3-class "each request exactly once" check is keyed per (request, cell) for a pair, with the single-profile key unchanged. If the gate finds this reaches the H0 check suite's sealed behaviour, it is a corner for L5 instead.
9. **Docs.** `docs/deploy-h100.md` LAUNCH SCHEMA v5 paragraph after the v4 section (`:168-200`); L9 owns the pin paragraphs. `docs/identity/read-old-table.md`: the L4c identity row and one read-old row per schema this slice bumps (launch v5, collection v2, the capture reference if bumped).
