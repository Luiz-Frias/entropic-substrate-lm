## Why (measured at `187553f`)

- `ladder/run/worker_command.py:212` names the pod worker's MLflow run `f"h-worker-{request.profile.identity}"`; its tag dict (`:215-219`) carries `schema`, `exp` and `config_hash` only. The sanctioned retry keeps `profile.identity` and changes the nonce, so every attempt of an arm shares one run name. `request.digest` (`ladder/run/worker_request.py:183`, a property, sha256 of the canonical request) is already in the worker's hands: `run_start` records it as `request_sha256` (`object_worker.py:117`), the stop marker binds to it (`:67,:80`). A fresh nonce changes the digest; a pod restart of the SAME request does not (E1 measured restart-loop duplicates), so same-digest duplicates can still exist and the attempts rule of DN-1646-ATTEMPTS stays load-bearing inside one identity.
- The wave monitor (`composition/entrypoints/h_wave_monitor.py`) already reads launch files: `_arms` (`:311-333`) parses each `--launch-file` with `parse_probe_launch(...).request` (`:321`) and builds `_Arm(run_name_for(request.profile.identity), total)` (`:322`); `H0ProbeLaunch.request` is a `ProbeRequest` (`h_probe_launch.py:153`), so `request.digest` is available at monitor time with no new input. `MlflowRestSource.latest(experiment_name, run_name)` (`:200`) queries `runs/search` with `filter = f"attributes.run_name = '{run_name}'"` (`:216`) after `_RUN_NAME.fullmatch` (`:201`); `RunSource` is the slice-5 protocol (`:128`), `_Arm` the dataclass (`:287`). `tests/test_h_wave_monitor.py:376` pins the exact filter string; `:498` pins the refusal of an unsafe run name before any request.
- The capture lane's `_validated_run_name` (`ladder/capture/reader/capture_results.py:211-228`) interpolates the run NAME into a capture path and refuses unsafe names; the H lane partitions on the `schema` tag (`:12`, `:94`). A new TAG touches neither; a new NAME shape would. The run-descriptor door (`ladder/capture/ports/run_descriptor.py:9-24`) fixes the FIELD SET (`tags: Mapping[...]` at `:62`), not the contents, so one more tag is co-resident content, not a door change (the FOR-1642 ticket text says the same; FOR-1654 lists `request_sha256` among the keys not yet on the run).
- `_emit` is defined three times: `worker/h_probe_controller.py:90-94` and `worker/h_probe_stop.py:45-49` are byte-identical (`diff` empty; signature `(level, event, pod_name, **fields)`, bound dict `{"pod_name": pod_name, **fields}`, `render(event, **bound)`), the monitor's `:291-292` lacks `pod_name`. The vocabulary leaf `worker/h_probe_log_events.py` (`render` at `:124`) is stdlib-only by slice-5 constraint C9, so the shared helper cannot live there. `h_probe_command.py` has no `_emit` (`:17` imports only `configure_logging`).
- Reader membership: `ladder/run/checkpoint.py:111` lists `ladder.run.worker_command`; no `ladder.run.worker.*` module is a member, so a new `worker/h_probe_host_log.py` is not one and `worker_command.py` is the ONE member in scope (DG-A). The conformance universe is unaffected: the new module is a library (no `main`), gets no `entrypoint: true` row (`tests/observability_conformance_config.py:97-102` keeps its eleven).
- Tests that spell `h-worker-`: `tests/test_h_run_descriptor.py` (`test_a_local_tiny_worker_omits_git_sha_and_image` `:198`, `test_a_remote_shaped_worker_carries_the_request_commit_and_image_unswapped` `:222`), `tests/test_h_wave_monitor.py`, `tests/test_h_lane_live.py`, `tests/test_capture_results.py`, `tests/test_mlflow_aggregate.py`, `tests/test_h_probe_events.py`, `tests/test_h_probe_log_events.py`.
